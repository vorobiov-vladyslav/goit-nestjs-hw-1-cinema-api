# Cinema API — ДЗ №1 «Back-end розробка з Node.js (NestJS)»

REST API кінотеатру: фільми, зали, сеанси та бронювання. За умовою домашнього завдання
база даних не підключається — усі дані зберігаються в масивах усередині сервісів і
зникають після перезапуску процесу.

## Технології

- **NestJS 11** + TypeScript (проєкт створено через NestJS CLI)
- **class-validator** / **class-transformer** — DTO та валідація; глобальний `ValidationPipe`
- **@nestjs/swagger** — Swagger UI на `/docs` з анотованими DTO та кодами відповідей
- **@nestjs/config** — читання `.env`
- Сховище — приватні масиви в сервісах (без БД)

## Встановлення та запуск

```bash
# 1. Встановити залежності
npm install

# 2. Створити локальний .env зі значеннями за замовчуванням
cp .env.example .env

# 3. Запуск у режимі розробки (аз змінами)
npm run start:dev

# або збірка та запуск зібраного застосунку
npm run build
npm run start:prod
```

Після запуску:

- API — http://localhost:3000
- Swagger UI — http://localhost:3000/docs

Доступні скрипти:

| Команда | Що робить |
|---|---|
| `npm install` | встановлює залежності |
| `npm run start:dev` | запуск у режимі розробки (`nest start --watch`) |
| `npm run build` | компіляція TypeScript у `dist/` |
| `npm run start:prod` | запуск зібраного застосунку (`node dist/main`) |
| `npm test` / `npm run test:e2e` | e2e-тести (Jest + supertest) |
| `npm run test:watch` | e2e-тести у watch-режимі |

## Архітектура

Проєкт поділений на модулі за доменами: `FilmsModule`, `HallsModule`, `ShowingsModule`,
`BookingsModule`. Кожен модуль містить контролер і сервіс:

- контролер приймає HTTP-запит, викликає сервіс і повертає відповідь;
- сервіс володіє приватним масивом — сховищем свого домену;
- ідентифікатори генеруються через `randomUUID()` з `node:crypto`.

Модулі спілкуються **лише через експортовані сервіси**, а не через прямі доступи до чужих масивів:

- `ShowingsService` перевіряє існування фільму й залу через `FilmsService` / `HallsService`;
- `FilmsService` / `HallsService` перевіряють залежні сеанси через `ShowingsService`
  (для розв'язання зустрічних залежностей модулів використано `forwardRef`);
- `BookingsService` працює з `ShowingsService` (існування сеансу, ціна) і `HallsService`
  (межі схеми залу).

Перевірки розділені за призначенням:

- **DTO + class-validator** — форма вхідних даних: наявність поля, тип, діапазон,
  формат рядка, унікальність місць у масиві (`IsUniqueSeats`), дата в майбутньому (`IsNotInPast`);
- **сервіс** — доменні правила, для яких потрібен стан сховища: існування фільму/залу,
  межі схеми залу, зайнятість місця, наявність залежних сеансів при видаленні;
- глобальний `ValidationPipe` з `whitelist: true` — поля, яких немає в DTO, до сервісу не потрапляють.

## API

Базова адреса: `http://localhost:3000`. Повна інтерактивна документація — `/docs`.

### Фільми

| Метод | Шлях | Опис |
|---|---|---|
| `POST` | `/films` | створити фільм |
| `GET` | `/films` | масив усіх фільмів |
| `GET` | `/films/:id` | один фільм |
| `PATCH` | `/films/:id` | оновити будь-яку підмножину полів |
| `DELETE` | `/films/:id` | видалити фільм (409, якщо на нього посилається сеанс) |

Модель `Film`: `id` (UUID), `title`, `durationMinutes` (ціле додатне), `releaseYear`.

### Зали

| Метод | Шлях | Опис |
|---|---|---|
| `POST` | `/halls` | створити зал (назва унікальна — інакше 409) |
| `GET` | `/halls` | масив усіх залів |
| `GET` | `/halls/:id` | зал разом із переліком місць `seats[{row, seat}]` |
| `DELETE` | `/halls/:id` | видалити зал (409, якщо на нього посилається сеанс) |

Модель `Hall`: `id` (UUID), `name`, `rows`, `seatsPerRow`. Перелік місць сервер обчислює
як `rows × seatsPerRow`; окремої сутності місця немає.

### Сеанси

| Метод | Шлях | Опис |
|---|---|---|
| `POST` | `/showings` | створити сеанс |
| `GET` | `/showings` | масив сеансів; необов'язкові query-параметри `filmId`, `date` (`YYYY-MM-DD`) |
| `GET` | `/showings/:id` | один сеанс |
| `GET` | `/showings/:id/seats` | схема місць залу з ознакою зайнятості |

Модель `Showing`: `id` (UUID), `filmId`, `hallId`, `startsAt` (ISO 8601, не в минулому),
`price` (ціна в копійках, ціле додатне). У відповідях `GET` замість `filmId`/`hallId`
повертаються назви: `filmTitle`, `hallName`. Сеанси відсортовані за часом початку,
при однаковому часі — за `id`. Параметр `date` порівнюється з UTC-датою початку сеансу
(`startsAt` нормалізується до ISO UTC).

### Бронювання

| Метод | Шлях | Опис |
|---|---|---|
| `GET` | `/bookings` | масив усіх бронювань |
| `POST` | `/showings/:id/bookings` | забронювати місця (201) |
| `GET` | `/showings/:id/bookings` | бронювання конкретного сеансу |
| `DELETE` | `/bookings/:id` | скасувати бронювання (204); місця знову вільні |

Модель `Booking`: `id` (UUID), `showingId`, `seats[{row, seat}]`, `totalPrice`
(`price × кількість місць`, у копійках). Повтор місця в запиті → 400; місце поза залом → 400; елемент `seats` має бути
обʼєктом з цілими додатними `row`/`seat`, інакше 400 (вкладені масиви, `{}` тощо);
хоча б одне вже заброньоване місце → 409 без часткового запису.

### Коди помилок

| Код | Коли |
|---|---|
| `400` | відсутнє поле, неправильний тип, явний `null` у `PATCH /films/:id`, число не ціле додатне, некоректна дата, дата в минулому, порожній масив `seats`, елемент `seats` не є обʼєктом з цілими `row`/`seat` (вкладені масиви, `{}`, відсутні поля), повтор місця в запиті, місце поза межами залу, неіснуючий `filmId`/`hallId` при створенні сеансу |
| `404` | фільм / зал / сеанс / бронювання з таким `id` не знайдено |
| `409` | зал з такою назвою вже існує; видалення фільму/залу, на який посилається сеанс; місце вже заброньоване на цьому сеансі |

## Тести

### E2E-тести (Jest + supertest)

У каталозі `test/` лежить набір e2e-тестів, який піднімає справжній Nest-застосунок
(зі справжніми модулями, сервісами, валідацією) і ходить у нього через HTTP — БД
не потрібна, бо сховища in-memory:

```bash
npm test          # або: npm run test:e2e
# Tests: 28 passed, 28 total

# Перевірка за фіксованого вечірнього UTC-часу (тест фільтрації за датою
# не залежить від моменту запуску):
FIXED_NOW=2026-11-07T22:30:00.000Z npm test
```

Що покрито (28 тестів):

- `films`: створення (201, UUID), валідація 400 (відсутнє поле / тип / недодатне число),
  `whitelist` (зайві поля не потрапляють у відповідь), список, `GET /:id`, 404,
  `PATCH` (часткове оновлення, 400/404, явний `null` для будь-якого поля → 400,
  порожнє тіло → 200 і поля не змінюються);
- `halls`: створення, унікальність назви (409), 400 на некоректні числа, список,
  `GET /:id` з 15 місцями для залу 3×5, 404;
- `showings`: усі 400 (неіснуючий фільм/зал, не-ISO дата, дата в минулому, дробова ціна),
  створення, сортування за `startsAt`, назви фільму/залу замість id, фільтри
  `filmId`/`date`, 400 на некоректну дату, `GET /:id`, 404, схема місць. Обидва сеанси
  для тесту `date` створюються на одній явно заданій UTC-добі, тому тест не залежить
  від часу запуску (перевіряється також із `FIXED_NOW`);
- `bookings`: створення з `totalPrice = price × seats`, списки, позначки `isBooked`,
  атомарний 409 без часткового запису, 400 (порожній масив, повтор місця, місце поза
  залом, елементи seats не є обʼєктами з цілими `row`/`seat` — вкладені масиви `[[]]`,
  `{}`, відсутні `row`/`seat`, не-числа), 404 для неіснуючого сеансу/бронювання,
  скасування 204 і звільнення місць;
- видалення: 409 для фільму/залу із сеансами, 404 для невідомих id, 204 для вільних.

### Smoke-тест (перевірка живого сервера)

`scripts/smoke-test.py` — окремий чорноскриньковий скрипт (лише стандартна бібліотека
Python): запускає сервер і перевіряє 92 твердження по HTTP, зокрема Swagger UI на `/docs`
та наявність усіх маршрутів в OpenAPI. Докладніше — в розділі нижче.

## Перевірка запитів (requests.http)

У корені репозиторію є `requests.http` — його можна виконувати послідовно згори вниз
у VS Code (розширення **REST Client**) або IntelliJ/WebStorm HTTP Client.

- спочатку створюються фільм, зал, сеанс і бронювання;
- ідентифікатори підставляються зі змінних (іменовані запити `# @name ...`), а не
  вписуються вручну;
- далі йдуть запити на кожну помилку, описану в ДЗ (400, 404, 409);
- наприкінці — успішні видалення та перевірки конфліктів при видаленні.

Швидка перевірка через `curl`:

```bash
# створити фільм
curl -s -X POST http://localhost:3000/films \
  -H 'Content-Type: application/json' \
  -d '{"title":"Inception","durationMinutes":148,"releaseYear":2010}'

# створити зал
curl -s -X POST http://localhost:3000/halls \
  -H 'Content-Type: application/json' \
  -d '{"name":"Червона зала","rows":3,"seatsPerRow":5}'

# усі сеанси
curl -s http://localhost:3000/showings
```

### Автоматична перевірка (опційно)

Після запуску сервера можна прогнати скрипт, який перевіряє всі успішні сценарії та кожен
код помилки (92 перевірки, без сторонніх бібліотек, лише стандартна бібліотека Python):

```bash
python3 scripts/smoke-test.py
# RESULT: 92 passed, 0 failed
```

Адресу можна змінити змінною `BASE_URL` (за замовчуванням `http://localhost:3000`).

## Обмеження

- Дані зберігаються в пам'яті й зникають після перезапуску — так вимагає ДЗ №1.
- Маршруту `DELETE /showings` у завданні немає, тому створений сеанс блокує видалення
  свого фільму й залу (409) — це очікувана поведінка за описом маршрутів.
- Проєкт розрахований на один процес без кластеризації (in-memory сховище).
